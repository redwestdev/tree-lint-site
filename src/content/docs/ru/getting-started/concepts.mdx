title: Концепции
description: 'Как Tree-lint распознаёт сущности и применяет правила: matches, rules, layers и groups.'
---

Tree-lint работает в два шага: сначала **распознаёт** сущности по имени и составу папки, затем **проверяет** их правилами. Правила применяются только к распознанным сущностям — от этого зависит, когда ждать сообщения об ошибке, а когда тишины.

Конфигурация состоит из пяти секций:

```ts
import { createConfig } from '@redwestdev/tree-lint';

export default createConfig({
  roots: ['src'], // директории для сканирования
  ignore: ['node_modules', 'dist'], // что пропускать
  entities: {}, // сущности
  layers: {}, // слои
  groups: {}, // группы (необязательно)
});
```

## `roots` и `ignore`

- `roots` — директории, внутри которых Tree-lint сканирует. Каждый корень сканируется независимо. По умолчанию используется текущий каталог.
- `ignore` — список micromatch-паттернов. Файлы и папки, совпавшие с паттерном, исключаются из сканирования. Паттерн сопоставляется с полным путём относительно проекта, например `"**/*.test.ts"` или `"**/__mocks__"`.

## Два шага: распознавание и проверка

Возьмём одно дерево и разберём на нём обе части:

```text
src/
└── components/
    ├── VeryLongComponentName/
    │   ├── VeryLongComponentName.tsx
    │   └── index.ts
    ├── Icon/
    │   └── Icon.tsx
    └── button/
        ├── Button.tsx
        └── index.ts
```

Конфиг описывает соглашение: компонент — это папка с именем, начинающимся с заглавной буквы, внутри которой обязательно есть файл `*.tsx` и `index.ts`. Имя папки не длиннее 20 символов:

```ts
export default createConfig({
  roots: ['src'],
  entities: {
    component: {
      matches: {
        type: 'directory',
        name: '[A-Z]*',
        children: [
          { type: 'file', name: '*.tsx' },
          { type: 'file', name: 'index.ts' },
        ],
      },
      rules: {
        nameLength: { type: 'error', max: 20 },
      },
    },
  },
  layers: {
    components: { entities: ['component'] },
  },
});
```

### Как работает `matches`

- `type` — `"file"` или `"directory"`: к какому виду узлов применяется сущность.
- `name` — micromatch-глоб для имени узла. Для файлов сопоставляется полное имя вместе с расширением.
- `children` — только для директорий: **обязательный состав**. Каждый перечисленный матчер должен найти себе отдельный дочерний элемент; лишние файлы и папки совпадению не мешают.

Сущность распознана, только если **все** матчеры совпали. Теперь три папки из дерева:

1. `VeryLongComponentName` — имя и состав совпали. Папка распознана как компонент, к ней применяются `rules`, и длина имени 22 символа нарушает `nameLength`:

   ```text
   src/components/VeryLongComponentName
     ✖ Name length is outside the allowed character limits

   Errors: 1, warnings: 0.
   ```

   Ошибка блокирует запуск: команда завершается с кодом `1`. Собственный текст сообщения задаётся полем `message` — пример в [Быстром старте](/ru/getting-started/quick-start/).

2. `Icon` — имя совпало, а состава нет (`index.ts` отсутствует). Папка **не распознана**, правила к ней не применяются. Вместо ошибки появится предупреждение распознавания:

   ```text
   src/components/Icon
     ⚠ It looks as component, but composition of child elements is invalid.
   ```

   Предупреждения не блокируют запуск: при `Errors: 0` команда завершается с кодом `0`.

3. `button` — состав совпал, а имя нет. Снова предупреждение, а не ошибка:

   ```text
   src/components/button
     ⚠ Name of component does not match the required pattern or convention.
   ```

   Если не совпали ни имя, ни состав (например, папка `styles/` с файлом `global.css`), папка просто не распознаётся — без сообщений и без правил.

### Почему правило «не сработало»

Распознавание всегда идёт раньше проверки. Если папка не совпала с `matches`, правила `rules` этой сущности к ней не применяются — в том числе `rules.name`. Поэтому:

- не задавайте в `matches.name` тот же глоб, что и в `rules.name.pattern`: правило просто продублирует уже пройденную проверку. Отдельное правило полезно, когда оно строже распознавания — например, `matches.name: "[A-Z]*"` распознаёт папку, а `rules.name.pattern: "[A-Z][a-z]*"` требует имя из букв;
- если нужно проверить папку, которая не проходит `matches`, ослабьте `matches` или воспользуйтесь [группами](#группы).

### Ошибка и предупреждение

- `type: "error"` — нарушение выводится как `✖`, команда завершается с кодом `1`. Подходит для CI.
- `type: "warning"` — нарушение выводится как `⚠`, на код выхода не влияет. Подходит для постепенного внедрения: сначала показать проблему, затем перевести в ошибку.

## Слои

**Слой** — папка, имя которой **точно** совпадает с ключом секции `layers` (глобы здесь не поддерживаются). Слои распознаются на любой глубине внутри `roots`:

```ts
layers: {
  components: {
    entities: ["component"], // сущности, которые распознаются внутри слоя
    rules: { isEmpty: { type: "warning" } }, // необязательные правила для самого слоя
  },
},
```

Сущности ищутся **только внутри слоёв** (или внутри другой сущности — см. [вложенные сущности](#вложенные-сущности)). Сущность, не перечисленная ни в одном слое, не будет распознана нигде. Если сослаться на необъявленную сущность, конфиг будет отклонён с ошибкой.

## Группы

**Группа** — способ применить правила к папке по паттерну имени, не объявляя её сущностью. В отличие от `layers` и `entities`, `groups` — это один объект, а не словарь:

```ts
groups: {
  name: "[a-z]*",            // необязательный глоб для имени папки
  children: [                // если указано — обязательный состав папки
    { type: "file", name: "*.test.ts" },
  ],
  rules: {
    nameLength: { type: "warning", max: 20 },
  },
},
```

Особенности групп:

- группа применяется только к «обычным» папкам — тем, что не стали слоями и не распознаны как сущности;
- внутри такой папки должен быть хотя бы один распознанный дочерний элемент: сущность или другая группа. Папка только с нераспознанными файлами под группу не попадёт;
- если задан `name` или `children` и совпадение неполное, выводится предупреждение распознавания — как у сущностей;
- `rules` применяются к самой папке.

## Вложенные сущности

Сущность-директория может объявить собственные вложенные сущности через поле `entities`:

```ts
entities: {
  page: {
    matches: { type: "directory", name: "[A-Z]*" },
    entities: ["section"], // внутри каждой страницы ищутся сущности "section"
  },

  section: {
    matches: {
      type: "directory",
      name: "[A-Z]*Sct",
      children: [{ type: "file", name: "index.ts" }],
    },
  },
},
```

Вложенные сущности распознаются только внутри той сущности, которая их объявила, — даже если они не перечислены ни в одном слое.

## Правила для дочерних элементов (`_matches`)

Правила сущности можно применить не к самой сущности, а к её дочерним элементам, совпавшим с паттерном:

```ts
entities: {
  component: {
    matches: {
      type: "directory",
      name: "[A-Z]*",
      children: [{ type: "file", name: "*.tsx" }],
    },
    rules: {
      children: [
        {
          _matches: { type: "file", name: "*.tsx" },
          lineCount: { type: "warning", max: 200 },
        },
      ],
    },
  },
},
```

Каждый дочерний элемент, совпавший с `_matches`, получает правила из этого же объекта. Записи в `children` без `_matches` игнорируются.

## Шаблоны `init`

`tree-lint init` генерирует готовую конфигурацию. Доступно два шаблона:

- **default** — типовые сущности (`component`, `hook`, `page`, `util`, `service`, `context`, `typeFile`) со своими слоями и примером правил для дочерних элементов с `_matches`.
- **deep-tree** — всё из `default` плюс секция `groups` и примеры проверок `custom()` для сущностей.

Оба шаблона — отправная точка: замените примеры сущностей на собственную архитектуру.
