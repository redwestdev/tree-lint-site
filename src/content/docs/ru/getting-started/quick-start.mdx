Этот раздел — один сквозной пример: от установки до исправленной ошибки. Все команды и конфиг относятся к одному и тому же маленькому проекту, поэтому шаги можно проходить по порядку и повторять на своём проекте.

Представим, что команда договорилась о структуре компонентов:

- каждый компонент лежит в собственной папке внутри `src/components`;
- имя папки начинается с заглавной буквы и не длиннее 20 символов;
- внутри папки обязательно есть файл с расширением `.tsx` и файл `index.ts`.

Папка `VeryLongComponentName` нарушает второе правило: в имени 22 символа.

Начнём с такого маленького проекта:

```
src/
└── components/
    └── VeryLongComponentName/
        ├── VeryLongComponentName.tsx
        └── index.ts
```

Создайте его в папке своего учебного проекта — например, `my-tree-lint-demo`, — или возьмите уже существующий проект с подобной структурой. Далее все шаги выполняются внутри этого проекта.

## 2. Опишите договорённости в конфиге

Создайте в корне проекта файл `tree-lint.config.ts`:

```ts
import { createConfig } from '@redwestdev/tree-lint';

export default createConfig({
  roots: ['src'], // где сканировать
  ignore: ['node_modules', 'dist'], // что пропускать

  entities: {
    component: {
      matches: {
        type: 'directory',
        name: '[A-Z]*', // имя папки начинается с заглавной буквы
        children: [
          // обязательный состав папки компонента
          { type: 'file', name: '*.tsx' },
          { type: 'file', name: 'index.ts' },
        ],
      },
      rules: {
        nameLength: {
          type: 'error',
          max: 20,
          message:
            'Имя папки компонента слишком длинное: уложитесь в 20 символов.',
        },
      },
    },
  },

  layers: {
    components: {
      entities: ['component'], // искать компоненты внутри папок components
    },
  },
});
```

Что здесь написано:

- `matches` — как **распознать** компонент: папка, имя которой начинается с заглавной буквы, с обязательным составом из `.tsx`-файла и `index.ts`. Распознавание само по себе не выводит ошибок — оно только решает, где применять правила.
- `rules.nameLength` — **проверка** для каждой распознанной папки: длина имени не больше 20 символов. `message` — собственный текст ошибки на русском.
- `layers.components` — компоненты распознаются только внутри папок с именем `components` на любой глубине внутри `roots`.

Как эти секции работают вместе, подробно разобрано в [Концепциях](/ru/getting-started/concepts/).

## 3. Запустите проверку


  </TabItem>
  <TabItem label='pnpm'>


  </TabItem>
  <TabItem label='yarn'>

  ```bash
  yarn tree-lint scan
  ```

В выводе — найденное нарушение:

```text
src/components/VeryLongComponentName
  ✖ Имя папки компонента слишком длинное: уложитесь в 20 символов.

Errors: 1, warnings: 0.

✖ Validation failed.
```

Что важно в этом выводе:

- нарушение относится к папке `VeryLongComponentName` — сканирование идёт от `src`;
- текст ошибки — ваш собственный `message`, а не служебное сообщение;
- при наличии ошибок команда завершается с кодом `1`, поэтому проверку можно встроить в CI.

Одни только предупреждения (`warning`) код выхода не меняют: при `Errors: 0` команда завершается с кодом `0`.

## 4. Исправьте нарушение и запустите снова

Переименуйте папку вместе с файлом внутри неё:

```
src/
└── components/
    └── Icon/
        ├── Icon.tsx
        └── index.ts
```

и повторите команду сканирования:

```text
Errors: 0, warnings: 0.

✔ Validation complete successfully!
```

Проверка прошла: структура соответствует конфигу, а следующее такое нарушение будет поймано ещё до ревью.

## 5. Закрепите проверку в команде

Добавьте скрипт в `package.json`:

```json
{
  "scripts": {
    "lint:tree": "tree-lint scan"
  }
}
```

Теперь локально можно запускать `npm run lint:tree`, `pnpm lint:tree` или `yarn lint:tree`.

В CI достаточно вызвать тот же скрипт — шаг упадёт при первой ошибке:

```yaml
- name: Lint file structure
  run: pnpm lint:tree
```

Тот же вызов подходит для pre-commit хука:

```bash
# .husky/pre-commit
pnpm lint:tree
```

## Создание конфига через `init`

Вместо файла вручную можно сгенерировать шаблон конфига командой:

```bash
tree-lint init
```

Команда создаёт файл `tree-lint.config` в текущем каталоге. Поддерживается интерактивный и неинтерактивный режим.

**Интерактивный режим** (TTY-терминал вне CI) - команда запросит недостающие параметры через prompt и предложит подтверждение перед созданием файла. Если выбор не устраивает, можно вернуться и указать параметры заново.

**Неинтерактивный режим** (CI) - все параметры должны быть переданы явно через флаги:

```bash
tree-lint init --format ts --type deep-tree
```

| Флаг                      | Возможные значения | Описание                  |
| ------------------------- | ------------------ | ------------------------- |
| `-f`, `--format <format>` | ts, js, json, yaml | Формат файла конфигурации |
| `-t`, `--type <type>`     | default, deep-tree | Шаблон конфигурации       |

Доступно два шаблона:

- **default** — набор типовых сущностей (`component`, `hook`, `page`, `util`, `service`, `context`, `typeFile`) с их слоями и правилами для дочерних элементов (см. [Концепции](/ru/getting-started/concepts/));
- **deep-tree** — те же сущности плюс секция `groups` и пример проверки `custom()`.

Сгенерированный шаблон — это готовая отправная точка для настройки: замените примеры сущностей на свою архитектуру.

## Форматы файла конфигурации

Поддерживаемые форматы файлов конфигурации:

- `tree-lint.config.ts` (рекомендуется)
- `tree-lint.config.js`
- `tree-lint.config.mjs` / `tree-lint.config.mts`
- `tree-lint.config.json`
- `tree-lint.config.yaml` / `tree-lint.config.yml`

При использовании конфигураций в формате `json` или `yaml` функциональность будет ограничена (нет поддержки кастомных правил через callback).

При сканировании Tree-lint ищет файл конфигурации, начиная с текущего каталога и поднимаясь вверх по дереву, поэтому команду можно запускать из любой подпапки проекта.

### Безопасность

> Конфигурация выполняется как код (TypeScript).
>
> **Важно:** Используйте Tree-lint только с доверенными конфигурациями. Если вы берете конфиг из стороннего источника, убедитесь в его безопасности, так как он может содержать вредоносный код.

## Флаги команды `scan`

Сканирование запускается командой `tree-lint scan` — так, как показано в сценарии выше. Дополнительные флаги команды:

| Флаг                              | Описание                                                                                                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `[path]`                          | Каталог для сканирования вместо текущего. Корни `roots` из конфига разрешаются относительно него, а сам конфиг по-прежнему ищется от текущего каталога вверх             |
| `-t`, `--tree-output [file]`      | Экспортировать сырую структуру файловой системы в JSON-файл. Без аргумента пишет `.project-tree.json` рядом с каталогом сканирования                                     |
| `-a`, `--annotated-output [file]` | Экспортировать обработанное дерево (с распознанными слоями, сущностями и группами) в JSON-файл. Без аргумента пишет `.entities-tree.json` рядом с каталогом сканирования |
| `-v`, `--vitals`                  | Показать метрики производительности движка (CPU, память и эффективность I/O)                                                                                             |
| `-p`, `--print-tree`              | Вывести проанализированную структуру проекта прямо в терминал                                                                                                            |
| `-c`, `--config-path [path]`      | Путь к файлу конфигурации. По умолчанию конфиг ищется от текущего каталога вверх                                                                                         |
| `-g`, `--group-by <type>`         | Изменить группировку результатов сканирования (по умолчанию "path")                                                                                                      |

> Короткий флаг `-t` означает разное в `init` (`--type`) и `scan` (`--tree-output`). В скриптах и CI лучше использовать длинные имена флагов, чтобы избежать путаницы.

Возможные значения для `--group-by` на примере сценария выше:

- `path` (по умолчанию) - группировка по пути в файловой системе:

  ```text
  src/components/VeryLongComponentName
    ✖ Имя папки компонента слишком длинное: уложитесь в 20 символов.
  ```

- `severity` - группировка по уровню (`error`, `warning`):

  ```text
  ✖ ERRORS:
    Имя папки компонента слишком длинное: уложитесь в 20 символов. - src/components/VeryLongComponentName
  ```

- `rule` - группировка по тексту нарушенного правила:

  ```text
  Имя папки компонента слишком длинное: уложитесь в 20 символов.
    ✖ src/components/VeryLongComponentName
  ```

## Возможные проблемы

- **"Configuration file not found"** — создайте конфиг командой `tree-lint init` или укажите существующий через `--config-path`.
- **Символические ссылки** — Tree-lint их не поддерживает и пропускает при сканировании.
- **Кастомные правила должны возвращать boolean** — любой другой результат callback в `custom()` считается нарушением.
- **В правиле `custom()` обязателен `type`** — без него Tree-lint 0.0.5 завершается внутренней ошибкой. См. [Использование проверки custom](/ru/rules/custom-usage/).
- **Правило `size` измеряется в килобайтах** — при этом `node.size` внутри `custom()` — в байтах. См. [Правила валидации](/ru/rules/).
- **Папка, содержащая только пустые файлы, считается пустой** — правило `isEmpty` проверяет суммарный размер узла. См. [Правила валидации](/ru/rules/).
