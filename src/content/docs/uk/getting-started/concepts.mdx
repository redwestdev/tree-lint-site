description: 'Як Tree-lint розпізнає сутності та застосовує правила: matches, rules, layers і groups.'
---

Tree-lint працює у два кроки: спочатку **розпізнає** сутності за іменем і складом папки, потім **перевіряє** їх правилами. Правила застосовуються лише до розпізнаних сутностей — від цього залежить, коли чекати на повідомлення про помилку, а коли — на тишу.

Конфігурація складається з п'яти секцій:

```ts
import { createConfig } from '@redwestdev/tree-lint';

export default createConfig({
  roots: ['src'], // каталоги для сканування
  ignore: ['node_modules', 'dist'], // що пропускати
  entities: {}, // сутності
  layers: {}, // шари
  groups: {}, // групи (необов'язково)
});
```

## `roots` та `ignore`

- `roots` — каталоги, всередині яких сканує Tree-lint. Кожен корінь сканується незалежно. За замовчуванням використовується поточний каталог.
- `ignore` — список micromatch-патернів. Файли й папки, що збігаються з патерном, виключаються зі сканування. Патерн порівнюється з повним шляхом відносно проєкту, наприклад `"**/*.test.ts"` або `"**/__mocks__"`.

## Два кроки: розпізнавання та перевірка

Візьмемо одне дерево і розберемо на ньому обидві частини:

```text
src/
└── components/
    ├── VeryLongComponentName/
    │   ├── VeryLongComponentName.tsx
    │   └── index.ts
    ├── Icon/
    │   └── Icon.tsx
    └── button/
        ├── Button.tsx
        └── index.ts
```

Конфіг описує домовленість: компонент — це папка з іменем, що починається з великої літери, у якій мають бути файл `*.tsx` та `index.ts`. Довжина імені папки — не більше ніж 20 символів:

```ts
export default createConfig({
  roots: ['src'],
  entities: {
    component: {
      matches: {
        type: 'directory',
        name: '[A-Z]*',
        children: [
          { type: 'file', name: '*.tsx' },
          { type: 'file', name: 'index.ts' },
        ],
      },
      rules: {
        nameLength: { type: 'error', max: 20 },
      },
    },
  },
  layers: {
    components: { entities: ['component'] },
  },
});
```

### Як працює `matches`

- `type` — `"file"` або `"directory"`: до яких вузлів застосовується сутність.
- `name` — micromatch-глоб для імені вузла. Для файлів порівнюється повне ім'я разом із розширенням.
- `children` — лише для каталогів: **обов'язковий склад**. Кожен перелічений матчер має знайти свій окремий дочірній елемент; зайві файли й папки не заважають збігу.

Сутність розпізнається лише якщо **всі** матчери збіглися. Тепер три папки з дерева:

1. `VeryLongComponentName` — збіглися ім'я та склад. Папку розпізнано як компонент, до неї застосовуються `rules`, а ім'я з 22 символів порушує `nameLength`:

   ```text
   src/components/VeryLongComponentName
     ✖ Name length is outside the allowed character limits

   Errors: 1, warnings: 0.
   ```

   Помилка блокує запуск: команда завершується з кодом `1`. Власний текст повідомлення задається полем `message` — приклад у [Швидкому старті](/uk/getting-started/quick-start/).

2. `Icon` — ім'я збіглося, але склад неповний (немає `index.ts`). Папку **не розпізнано**, і жодні правила до неї не застосовуються. Замість помилки з'являється попередження розпізнавання:

   ```text
   src/components/Icon
     ⚠ It looks as component, but composition of child elements is invalid.
   ```

   Попередження не блокують запуск: з `Errors: 0` команда завершується з кодом `0`.

3. `button` — склад збігся, але ім'я ні. Знову попередження, а не помилка:

   ```text
   src/components/button
     ⚠ Name of component does not match the required pattern or convention.
   ```

   Якщо ж не збіглися ні ім'я, ні склад (наприклад, папка `styles/` з файлом `global.css`), папку просто не розпізнано — без повідомлень і без правил.

### Чому правило «не спрацювало»

Розпізнавання завжди передує перевірці. Якщо папка не відповідає `matches`, `rules` цієї сутності до неї не застосовуються — включно з `rules.name`. Тому:

- не задавайте один і той самий глоб у `matches.name` і `rules.name.pattern`: правило лише продублює перевірку, яка вже пройшла. Окреме правило корисне, коли воно суворіше за розпізнавання — наприклад, `matches.name: "[A-Z]*"` розпізнає папку, а `rules.name.pattern: "[A-Z][a-z]*"` вимагає ім'я лише з літер;
- щоб перевірити папку, яка не проходить `matches`, послабте `matches` або скористайтеся [групами](#groups).

### Помилка та попередження

- `type: "error"` — порушення виводиться як `✖`, команда завершується з кодом `1`. Підходить для CI.
- `type: "warning"` — порушення виводиться як `⚠` і не впливає на код виходу. Підходить для поступового впровадження: спочатку покажіть проблему, потім перетворіть її на помилку.

## Шари

**Шар** — це папка, ім'я якої **точно** збігається з ключем секції `layers` (глоби тут не підтримуються). Шари розпізнаються на будь-якій глибині всередині `roots`:

```ts
layers: {
  components: {
    entities: ["component"], // сутності, що розпізнаються всередині шару
    rules: { isEmpty: { type: "warning" } }, // необов'язкові правила для самого шару
  },
},
```

Сутності шукаються **лише всередині шарів** (або всередині іншої сутності — див. [вкладені сутності](#вкладені-сутності)). Сутність, не вказана в жодному шарі, ніколи не буде розпізнана. Посилання на неоголошену сутність робить конфіг недійсним із помилкою.

## Групи

**Група** — спосіб застосувати правила до папки за патерном імені, не оголошуючи її сутністю. На відміну від `layers` та `entities`, `groups` — це єдиний об'єкт:

```ts
groups: {
  name: "[a-z]*",            // необов'язковий глоб для імені папки
  children: [                // якщо задано — обов'язковий склад папки
    { type: "file", name: "*.test.ts" },
  ],
  rules: {
    nameLength: { type: "warning", max: 20 },
  },
},
```

Особливості груп:

- група застосовується лише до «звичайних» папок — тих, що не стали шарами і не розпізнані як сутності;
- у папці має бути хоча б один розпізнаний дочірній елемент: сутність або інша група. Папка лише з нерозпізнаними файлами під групу не потрапляє;
- якщо задано `name` або `children` і збіг частковий, виводиться попередження розпізнавання — так само, як для сутностей;
- `rules` застосовуються до самої папки.

## Вкладені сутності

Сутність-каталог може оголосити власні вкладені сутності через поле `entities`:

```ts
entities: {
  page: {
    matches: { type: "directory", name: "[A-Z]*" },
    entities: ["section"], // всередині кожної сторінки шукаються сутності "section"
  },

  section: {
    matches: {
      type: "directory",
      name: "[A-Z]*Sct",
      children: [{ type: "file", name: "index.ts" }],
    },
  },
},
```

Вкладені сутності розпізнаються лише всередині сутності, яка їх оголосила, — навіть якщо їх не вказано в жодному шарі.

## Правила для дочірніх елементів (`_matches`)

Правила сутності можна застосувати не до самої сутності, а до її дочірніх елементів, що збігаються з патерном:

```ts
entities: {
  component: {
    matches: {
      type: "directory",
      name: "[A-Z]*",
      children: [{ type: "file", name: "*.tsx" }],
    },
    rules: {
      children: [
        {
          _matches: { type: "file", name: "*.tsx" },
          lineCount: { type: "warning", max: 200 },
        },
      ],
    },
  },
},
```

Кожен дочірній елемент, що збігається з `_matches`, отримує правила з того самого об'єкта. Записи в `children` без `_matches` ігноруються.

## Шаблони `init`

`tree-lint init` генерує готовий конфіг. Доступні два шаблони:

- **default** — типові сутності (`component`, `hook`, `page`, `util`, `service`, `context`, `typeFile`) з їхніми шарами та прикладом правил для дочірніх елементів із `_matches`.
- **deep-tree** — усе з `default` плюс секція `groups` і приклади перевірки `custom()` для сутностей.

Обидва шаблони — відправна точка: замініть прикладові сутності на власну архітектуру.
