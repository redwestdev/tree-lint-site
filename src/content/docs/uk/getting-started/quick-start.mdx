Цей розділ — один наскрізний приклад: від встановлення до виправленого порушення. Усі команди та конфіг належать одному невеликому проєкту, тож кроки можна проходити по порядку і повторювати на власному проєкті.

Уявіть, що команда домовилася про структуру компонентів:

- кожен компонент живе в окремій папці всередині `src/components`;
- ім'я папки починається з великої літери і не довше ніж 20 символів;
- у папці мають бути файл із розширенням `.tsx` та файл `index.ts`.

Папка `VeryLongComponentName` порушує друге правило: її ім'я — 22 символи.

Почнемо з невеликого проєкту з такою структурою:

```text
src/
└── components/
    └── VeryLongComponentName/
        ├── VeryLongComponentName.tsx
        └── index.ts
```

Створіть його в папці навчального проєкту — наприклад, `my-tree-lint-demo` — або візьміть наявний проєкт зі схожою структурою. Усі наступні кроки виконуються всередині цього проєкту.

## 2. Опишіть домовленості в конфігу

Створіть файл `tree-lint.config.ts` у корені проєкту:

```ts
import { createConfig } from '@redwestdev/tree-lint';

export default createConfig({
  roots: ['src'], // де сканувати
  ignore: ['node_modules', 'dist'], // що пропускати

  entities: {
    component: {
      matches: {
        type: 'directory',
        name: '[A-Z]*', // ім'я папки починається з великої літери
        children: [
          // обов'язковий склад папки компонента
          { type: 'file', name: '*.tsx' },
          { type: 'file', name: 'index.ts' },
        ],
      },
      rules: {
        nameLength: {
          type: 'error',
          max: 20,
          message: "Ім'я папки компонента задовге: вкладіться у 20 символів.",
        },
      },
    },
  },

  layers: {
    components: {
      entities: ['component'], // шукати компоненти всередині папок components
    },
  },
});
```

Що тут описано:

- `matches` — як **розпізнати** компонент: папка з іменем, що починається з великої літери, та обов'язковим складом — файл `.tsx` та `index.ts`. Саме розпізнавання не виводить помилок — воно лише вирішує, де застосовуються правила.
- `rules.nameLength` — **перевірка** для кожної розпізнаної папки: довжина імені не має перевищувати 20 символів. `message` — ваш власний текст помилки.
- `layers.components` — компоненти розпізнаються лише всередині папок з іменем `components` на будь-якій глибині в `roots`.

Як ці секції працюють разом — детально в [Концепціях](/uk/getting-started/concepts/).

## 3. Запустіть перевірку

<Tabs syncKey='pkg'>
  <TabItem label='npm'>

  ```bash
  npx tree-lint scan
  ```

  </TabItem>
  <TabItem label='pnpm'>

  ```bash
  pnpm exec tree-lint scan
  ```

  </TabItem>
  <TabItem label='yarn'>

  ```bash
  yarn tree-lint scan
  ```

  </TabItem>
</Tabs>

Вивід показує знайдене порушення:

```text
src/components/VeryLongComponentName
  ✖ Ім'я папки компонента задовге: вкладіться у 20 символів.

Errors: 1, warnings: 0.

✖ Validation failed.
```

Що важливо в цьому виводі:

- порушення належить папці `VeryLongComponentName` — сканування починається від `src`;
- текст помилки — ваш власний `message`, а не службове повідомлення;
- за наявності помилок команда завершується з кодом `1`, тож перевірку можна вбудувати в CI.

Самі попередження не змінюють код виходу: з `Errors: 0` команда завершується з кодом `0`.

## 4. Виправте порушення і запустіть ще раз

Перейменуйте папку разом із файлом усередині:

```text
src/
└── components/
    └── Icon/
        ├── Icon.tsx
        └── index.ts
```

і повторіть команду сканування:

```text
Errors: 0, warnings: 0.

✔ Validation complete successfully!
```

Перевірка пройдена: структура відповідає конфігу, і наступне таке порушення буде знайдено ще до рев'ю.

## 5. Закріпіть перевірку в команді

Додайте скрипт у `package.json`:

```json
{
  "scripts": {
    "lint:tree": "tree-lint scan"
  }
}
```

Тепер локально можна запускати `npm run lint:tree`, `pnpm lint:tree` або `yarn lint:tree`.

У CI достатньо викликати той самий скрипт — крок упаде на першій помилці:

```yaml
- name: Lint file structure
  run: pnpm lint:tree
```

Той самий виклик пасує й хуку pre-commit:

```bash
# .husky/pre-commit
pnpm lint:tree
```

## Створення конфіга через `init`

Замість того, щоб писати файл вручну, можна згенерувати шаблон конфіга:

```bash
tree-lint init
```

Команда створює файл `tree-lint.config` у поточному каталозі. Підтримуються інтерактивний і неінтерактивний режими.

**Інтерактивний режим** (термінал із TTY поза CI) — команда запитує відсутні параметри та просить підтвердження перед створенням файлу. Якщо вибір не влаштовує, можна повернутися і вказати параметри знову.

**Неінтерактивний режим** (CI) — усі параметри потрібно передати явно через прапорці:

```bash
tree-lint init --format ts --type deep-tree
```

| Прапорець                 | Можливі значення   | Опис                      |
| ------------------------- | ------------------ | ------------------------- |
| `-f`, `--format <format>` | ts, js, json, yaml | Формат файла конфігурації |
| `-t`, `--type <type>`     | default, deep-tree | Шаблон конфігурації       |

Доступні два шаблони:

- **default** — набір типових сутностей (`component`, `hook`, `page`, `util`, `service`, `context`, `typeFile`) з їхніми шарами та правилами для дочірніх елементів (див. [Концепції](/uk/getting-started/concepts/));
- **deep-tree** — ті самі сутності плюс секція `groups` і приклад перевірки `custom()`.

Згенерований шаблон — готова відправна точка для налаштування: замініть прикладові сутності на власну архітектуру.

## Формати файлів конфігурації

Підтримувані формати файлу конфігурації:

- `tree-lint.config.ts` (рекомендований)
- `tree-lint.config.js`
- `tree-lint.config.mjs` / `tree-lint.config.mts`
- `tree-lint.config.json`
- `tree-lint.config.yaml` / `tree-lint.config.yml`

З конфігами у форматі `json` або `yaml` функціональність обмежена (немає підтримки кастомних правил через колбеки).

Під час сканування Tree-lint шукає файл конфігурації, починаючи з поточного каталогу і вгору по дереву, тож команду можна запускати з будь-якої підпапки проєкту.

### Безпека

> Конфігурація виконується як код (TypeScript).
>
> **Важливо:** Використовуйте Tree-lint лише з перевіреними конфігами. Якщо берете конфіг від третіх осіб, переконайтеся, що він безпечний: він може містити шкідливий код.

## Прапорці команди `scan`

Сканування запускається командою `tree-lint scan` — як у сценарії вище. Додаткові прапорці:

| Прапорець                         | Опис                                                                                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[path]`                          | Каталог для сканування замість поточного. `roots` із конфіга обчислюються відносно нього, а конфіг, як і раніше, шукається від поточного каталогу вгору         |
| `-t`, `--tree-output [file]`      | Експорт сирої файлової структури у файл JSON. Без аргумента записує `.project-tree.json` поруч із каталогом сканування                                          |
| `-a`, `--annotated-output [file]` | Експорт обробленого дерева (з розпізнаними шарами, сутностями й групами) у файл JSON. Без аргумента записує `.entities-tree.json` поруч із каталогом сканування |
| `-v`, `--vitals`                  | Показати метрики продуктивності рушія (CPU, пам'ять і ефективність вводу/виводу)                                                                                |
| `-p`, `--print-tree`              | Вивести проаналізовану структуру проєкту в термінал                                                                                                             |
| `-c`, `--config-path [path]`      | Шлях до файлу конфігурації. За замовчуванням конфіг шукається від поточного каталогу вгору                                                                      |
| `-g`, `--group-by <type>`         | Змінити групування результатів сканування (за замовчуванням "path")                                                                                             |

> Короткий прапорець `-t` означає різне в `init` (`--type`) та `scan` (`--tree-output`). У скриптах і CI краще використовувати довгі імена прапорців, щоб уникнути плутанини.

Можливі значення `--group-by` на прикладі сценарію вище:

- `path` (за замовчуванням) — групування за шляхом у файловій системі:

  ```text
  src/components/VeryLongComponentName
    ✖ Ім'я папки компонента задовге: вкладіться у 20 символів.
  ```

- `severity` — групування за рівнем (`error`, `warning`):

  ```text
  ✖ ERRORS:
    Ім'я папки компонента задовге: вкладіться у 20 символів. - src/components/VeryLongComponentName
  ```

- `rule` — групування за текстом порушеного правила:

  ```text
  Ім'я папки компонента задовге: вкладіться у 20 символів.
    ✖ src/components/VeryLongComponentName
  ```

## Типові проблеми

- **"Configuration file not found"** — створіть конфіг командою `tree-lint init` або вкажіть наявний через `--config-path`.
- **Custom rules must return a boolean** — будь-який інший результат колбека в `custom()` зараховується як порушення.
- **У `custom()` обов'язковий `type`** — без нього Tree-lint 0.0.5 падає з внутрішньою помилкою. Див. [Використання перевірки custom](/uk/rules/custom-usage/).
- **Правило `size` вимірюється в кілобайтах** — а `node.size` усередині `custom()` — у байтах. Див. [Правила валідації](/uk/rules/).
- **Папка, що містить лише порожні файли, вважається порожньою** — правило `isEmpty` перевіряє загальний розмір вузла. Див. [Правила валідації](/uk/rules/).
